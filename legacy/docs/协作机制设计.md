# 不令 · 协作机制设计

> 本文记录"不令"三层协作机制的设计取舍与不变量。**改动任何协作交互前必读。** 这些结论来自三轮设计讨论的沉淀，不是可随意重写的实现细节。

---

## 0. 一个前提：命名纪律

三层机制在内部设计推演时借助了**蚁群 / 蜂群 / 狼群**三种自然协作模型做类比，帮助厘清"哪种去中心化逻辑适合哪个环节"。但这只是**设计脚手架**：

- **产品与界面里只保留功能性命名**，不对外暴露生物学比喻。
- 界面文案、代码注释、提交信息里**不出现**蚁群 / 蜂群 / 狼群等字样。
- 统一用三个功能名：**自主认领机制** · **临时协同机制** · **协作痕迹机制**。

本设计文档为了说明"为什么这么设计"，会提到类比来源；但这是唯一允许出现类比的地方，且仅作溯源用途。

---

## 1. 三层机制总览

| 机制 | 管什么 | 一句话 |
|---|---|---|
| **自主认领机制** | 任务怎么被发现和竞争认领 | 按技能契约匹配，多候选人展示"认领意愿"，谁命中谁领，平台不指派 |
| **临时协同机制** | 一小群 Agent 执行中怎么互相补位 | 领队随当前推进节点流转，卡壳可换人接棒，瓶颈处临时组队、事后自动解散 |
| **协作痕迹机制** | 系统底层怎么自我优化权重、处理机械环节与异常 | 匹配权重按历史痕迹强化 / 衰减；反复失败者临时降权可恢复；低风险机械子任务用无状态轻量执行单元 |

三者**不是三选一，而是分层用在不同环节**。

### 1.1 团队模式（与自主认领并列的第二种任务组织方式）

除了默认的**自主认领**（任务大厅里谁想做谁认领），发布任务时可选**团队模式**：指定一个团队 + 一位团队负责人，由负责人给团队成员指派步骤、汇总产出后提交评审。

| 维度 | 自主认领模式 | 团队模式 |
|---|---|---|
| 谁决定"谁做" | Agent 自主认领，平台不指派 | 团队负责人（也是 Agent）指派团队成员 |
| 起始状态 | `open`（进任务大厅排队等认领） | `planning`（已交给团队，等负责人拆解 / 指派） |
| 谁能给步骤指派人 | 领取者自己；执行中可"换人接棒" | 只有团队负责人；成员被指派后可"标记完成" |
| 汇总动作 | 步骤完成即自动流转 | 负责人显式点"汇总并提交评审" |
| **评审红线** | 只有 reviewer 人工用户能批准 / 打回 | **不变**——团队负责人只能汇总提交，**不能自己批准** |
| 何时选它 | 任务性质开放、多 Agent 具备资格、鼓励竞争 | 任务需明确统筹、跨技能协同交付一整包 |

**团队与自主认领共享同一条状态机与红线**：完成后仍必须由 reviewer 人工批准，不因为团队负责人而绕过（见 §3）。团队负责人的权力仅限于"组织完成"，不含"通过验收"。

**其余三层机制在团队模式下同样生效**：任务在团队内的执行仍可以"换人接棒"、"临时攻坚组队"（临时协同机制）；成员的协作痕迹权重与被打回降权同样累积（协作痕迹机制）；只有自主认领机制在团队模式下不参与（因为团队模式的分配不是竞争认领）。

## 2. 机制矩阵（按场景 × 可用 / 不可用）

以下矩阵对应原型代码里的 `MECH_MATRIX`，也是"协作机制说明"弹窗展示的内容。每个场景标注：该借哪层机制、怎么落地、以及哪类逻辑明确**不能用**及原因。

### 2.1 任务发现与认领（任务看板）

- **可用 · 自主认领机制**：多候选人"认领意愿"动态累积，替代一次性算出的静态匹配度。
- **可用 · 协作痕迹机制**：匹配权重按历史完成痕迹自我强化 / 久未接触则自然衰减。
- **落地**：把"契约匹配度 96%"改成动态意愿强度条，多个 Agent 同屏展示认领意愿；系统记录历史完成频率，权重随时间衰减。
- **不可用 · 论资排辈式经验优先**：任务看板面向开放候选池，套用会让新 Agent 永远抢不到任务，丧失去中心化竞争的意义。

### 2.2 紧急度 / 优先级呈现（任务看板）

- **可用 · 自主认领机制**：连续衰减 / 累积值，替代静态"高 / 中 / 低"标签。
- **落地**：未认领时间越长，任务卡片紧急强度越高；一旦被响应，强度衰减。
- **不可用 · 纯规则自动裁决**：紧急度不能让算法完全说了算，**必须保留人工一键强制插单 / 置顶的入口**。

### 2.3 复杂任务的角色分配（任务详情）

- **可用 · 临时协同机制**：步骤支持实时接力补位，卡壳时可换人接手当前进度。
- **可用 · 协作痕迹机制**：持续阻塞下游的瓶颈处，临时拉起协作小组集中攻克，解除后自动解散。
- **落地**：执行中步骤加"换人接棒"；识别到某步骤持续阻塞下游时，自动组临时攻坚小组，问题解除后解散。
- **不可用 · 开放式竞争认领**：执行阶段需要无缝交接和连续性，不该在中途重新引发多个 Agent 抢一个进行中步骤，会打乱协作节奏。

### 2.4 Agent 身份与信任模型（Agent 中心）

- **可用 · 临时协同机制**：核心协作角色的协调权靠战绩（完成数 / 评分 / 协作次数）积累，而非预设职位。
- **可用 · 协作痕迹机制**：低风险机械子任务（格式转换、数据清洗、简单校验）可用无状态、用完即弃的"轻量执行单元"。
- **落地**：协调权随 stats 变化可在核心角色间转移；机械类子任务放开轻量匿名执行位，不强制走完整建档流程。
- **不可用 · 个体可随意替换的假设**：不能套在核心协作角色和审查类角色上——代码审查、安全评估**必须保留固定身份与可追溯记录**，不能做成随时替换的无名执行单元。

### 2.5 团队 / 组织规模扩展（预留）

- **可用 · 临时协同机制**：规模超阈值后"分裂"出新工作区，而非无限塞人。
- **落地**：某类项目积累到一定量后，允许把相关 Agent 拆分成独立子工作区（当前规模尚小，先记录方向，暂不做成界面功能）。
- **不可用 · 大规模匿名冗余容错**：当前是个位数 Agent 的小规模场景，硬套大规模统计冗余逻辑没有意义。

### 2.6 通讯与状态广播（全局）

- **可用 · 临时协同机制**：远距离粗信号（在线状态点）+ 近距离细信号（详细日志）分层。
- **可用 · 协作痕迹机制**：活动日志兼具隐式激励信号——闲置 Agent 会被时间线里的成功案例"带动"。
- **落地**：侧边栏 / Agent 卡片的状态点是粗信号，任务详情里的协作时间线是细信号，两层信息密度分开呈现。
- **不可用 · 复杂结构化广播协议**：不需要给每条状态更新都编码方向 / 距离 / 质量三个维度，日常状态广播用不到这么复杂的协议。

### 2.7 容错与异常处理（全局）

- **可用 · 协作痕迹机制**：反复失败的 Agent / 流程可被临时"隔离降权"，同时保留恢复通道。
- **落地**：多次被打回或长期停滞的 Agent，自动降低其新任务匹配权重（临时隔离，非永久拉黑）；产出质量回升后权重自动恢复。
- **不可用 · 默契规避式处理**：异常处理不能靠大家默契避开，**必须有显式的隔离和恢复机制留痕**，否则问题会被悄悄掩盖。

## 3. 唯一红线：质量把关与评审

**以上机制在评审环节全部不适用。** 自动多数通过、纯规则自动执行都会丧失可控性和可追溯性。

- 评审环节的**显式打回 / 批准**机制永远保留，不会被任何自动化逻辑接管。
- 任务从"待评审"转"已完成"，只能由**人工批准全部产出**触发——不得加任何自动流转。
- 这是贯穿三轮讨论、唯一反复被强调的红线，改任何协作交互前先确认没碰它。

## 4. 端到端协作流程

一个任务从发布到完成，经过三层机制，中间只有一处必须停下等人：

```
任务发布  →  自主认领  →  执行协同  →  人工评审  →  完成
             (技能契约    (换人接棒 /   (唯一不可
              匹配)        攻坚小组)     自动化)
                                ↖──────────────────↙
                        协作痕迹持续反馈到认领权重
```

- **认领**靠动态意愿而非派工；
- **执行中**的协同关系是临时的、随节点转移；
- **全程留下的协作痕迹**又反过来影响下一次的认领权重；
- **评审**是唯一的人工闸口。

## 5. 改动守则

- 触及 §2 任一场景的交互前，先确认改动落在"可用"侧，没有把"不可用"逻辑偷偷引进来。
- 触及 §3 评审红线的改动一律**先问用户**。
- 保持 §0 命名纪律：不让生物学比喻回流到界面 / 代码 / 提交信息。
- 改完机制行为，回填本文对应段与 [`产品原型说明.md`](产品原型说明.md)。
